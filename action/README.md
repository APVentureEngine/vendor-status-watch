# Vendor Status Watch — GitHub Action

**Tell your Slack, Discord or Teams channel the moment a vendor you depend on
breaks — from your own GitHub Actions, with no account and no API key.**

```yaml
- uses: APVentureEngine/vendor-status-watch-action@v1
  with:
    vendors: github,openai,cloudflare,stripe
    webhook-url: ${{ secrets.WEBHOOK_URL }}
```

That is the whole setup. The action polls each vendor's own public status page,
diffs it against the last run, and posts one message per change.

---

## Why this exists

Status pages are the only place a vendor admits it is down, and nobody watches
1,100 of them. Commercial aggregators start around $30–$100/month for a handful
of vendors. This action does the watching part for free, inside infrastructure
you already pay for, and the only thing that ever leaves your repository is the
POST to the webhook you configured.

It is backed by a **living map of SaaS status pages that is rebuilt every day**:

| | |
|---|---|
| Vendors mapped | **1,127** |
| Machine-readable (pollable) | **799** |
| Incidents in the public history | **14,707** |
| Incidents in the last 30 days | **2,195** |
| Map rebuilt | **daily** |

Because the map is fetched fresh at run time, a vendor that moves its status
page, or a vendor added upstream last night, starts working for you without you
touching anything. Numbers above are from
[`stats.json`](https://approjects-vendor-status-watch.static.hf.space/api/stats.json),
regenerated by the same daily pipeline.

Type vendors the way you say them — `aws`, `gcp`, `m365`, `Google Cloud` and the map's own slugs all resolve, and any name that does not match is printed in the job log (never skipped silently). Browse the list:
**<https://approjects-vendor-status-watch.static.hf.space/vendors.html>**

## What it sends

| Event | When |
|---|---|
| `WATCHING` | first run for a vendor — one summary line, existing incidents baselined silently |
| `INCIDENT` | an incident id appears that was not there last run |
| `UPDATE` | a known incident changes state or gets a new update |
| `RESOLVED` | a known incident disappears from the vendor's page |
| `CANNOT SEE` | the vendor failed to parse N runs in a row — **one** alert, then silence |
| `VISIBLE AGAIN` | that vendor parses again |

A vendor it cannot see is reported as **UNKNOWN, never as OK**. A monitor that
goes quiet when it breaks is worse than no monitor.

Slack gets Block Kit, Discord gets embeds, Teams gets an Adaptive Card, anything
else gets plain JSON. Detection is automatic from the webhook host; override it
with `format:`.

## Full example

State must survive between runs or every run re-baselines and you hear nothing.
Cache it:

```yaml
name: vendor status watch
on:
  schedule:
    - cron: '*/10 * * * *'
  workflow_dispatch:

jobs:
  watch:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    concurrency:
      group: vendor-status-watch
      cancel-in-progress: false
    steps:
      - uses: actions/cache/restore@v4
        with:
          path: .vendor-status-watch
          key: vsw-state-${{ github.run_id }}
          restore-keys: vsw-state-

      - uses: APVentureEngine/vendor-status-watch-action@v1
        with:
          vendors: github,openai,cloudflare,stripe,slack
          webhook-url: ${{ secrets.WEBHOOK_URL }}
          format: auto

      - uses: actions/cache/save@v4
        if: always()
        with:
          path: .vendor-status-watch
          key: vsw-state-${{ github.run_id }}
```

Prefer state in git? Set `state-path: state.json`, drop the cache steps, and
commit the file back with `contents: write`.

## Inputs

| Input | Required | Default | Meaning |
|---|---|---|---|
| `vendors` | yes | — | Comma-separated names or slugs, e.g. `github,aws,openai`. Unmatched names are reported in the log. |
| `webhook-url` | yes | — | Slack / Discord / Teams / any JSON endpoint. **Use a secret.** |
| `format` | no | `auto` | `auto`, `slack`, `discord`, `teams`, `json`. |
| `state-path` | no | `.vendor-status-watch/state.json` | Relative to the workspace. |
| `unreachable-after` | no | `3` | Failed polls before one "cannot see" alert. |
| `mute-maintenance` | no | `false` | `true` ignores maintenance windows. |
| `map-url` | no | upstream | Override the living vendor map. |
| `dry-run` | no | `false` | Poll, print payloads, post nothing. |

**Output:** `state-path` — the absolute path of the state file the run wrote.

---

## What it does not do

- It does not check whether *your* service is up. It reads what your **vendors**
  publish. Pair it with a real uptime checker.
- 328 of the 1,127 mapped vendors publish no machine-readable feed; those are
  listed on the site but cannot be polled. It will tell you rather than pretend.
- Scheduled Actions are delayed under load; treat the cron as "roughly".

## Privacy

Standard-library Python. The only outbound requests are the public status
endpoints and your webhook. No telemetry, no account, no key.
